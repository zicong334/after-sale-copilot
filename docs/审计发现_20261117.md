## B1 — 买家历史消息接口泄露坐席内部备注(**隐私**)✅ 已修

### 实测(真实 HTTP,enforce 模式,真实买家 JWT)

坐席在工单里写一条内部备注 `is_internal=True`,内容
`内部备注:该买家疑似恶意退款,先拖延处理,勿告知客户`;另写一条正常回复。
买家 `buyer_demo` 取自己会话的历史:

```
GET /api/c/sessions/{sid}/messages -> 200
返回 2 条消息:
  author=agent is_internal=False content='您好,已为您登记,正在核实。'
  author=agent is_internal=True  content='内部备注:该买家疑似恶意退款,先拖延处理,勿告知客户'
```

**内部备注原文完整出现在买家可见的响应体里。**
对照:换成另一个买家的 token 取同一会话 → **404**(会话归属校验本身是好的),
所以问题**不是越权**,而是**这条路径没做内部备注过滤**。

### 根因:三条路径两条过滤、一条没过滤

| 路径 | 是否过滤内部备注 | 位置 |
|---|---|---|
| WS 实时推送 | ✅ 过滤 | [`api/agent.py:464`](../backend/app/api/agent.py:464) `if not message.is_internal:` 才广播 |
| 买家前端渲染 | ✅ 跳过 | [`frontend/app.js:750`](../frontend/app.js:750) `if (msg.is_internal === true) return;` |
| **买家历史 REST** | ❌ **不过滤** | [`api/chat.py:678-689`](../backend/app/api/chat.py:678) 把该会话所有 `ticket_message` 全量 append,只带 `is_internal` 标记 |

**前端不渲染 ≠ 数据没给出去**。任何持买家 token 的人直接调 API 就能读到全部内部备注;
浏览器 DevTools、抓包、脚本都能拿到。坐席内部备注常含风控判断、客户评价、处置策略,
属**不该对客户可见**的信息。

### 为什么测试没抓到

`tests/test_agent_workbench.py:321` 有一条看着像的断言:
```python
assert all(item["is_internal"] is False for item in buyer)
```
但它测的是**坐席端** `/api/b/tickets/{id}`,且 `buyer` 是
`[item for item in messages if item["author_type"] == "user"]`
——只断言**买家自己发的**消息不带内部标记,**完全没有覆盖「坐席内部备注不得返给买家」**。
全仓搜不到针对 `/api/c/sessions/{id}/messages` 的内部备注过滤用例。

### 建议修法

在 `session_messages` 合并 `ticket_message` 时,对**非坐席身份**跳过 `is_internal=True` 的行
(而不是只打标记):
```python
for row in ticket_rows:
    if row.is_internal and identity.role != "agent" and not identity.is_internal:
        continue
```
更稳妥的做法是**默认不返回**,只有显式的坐席端投影才带内部备注(白名单而非黑名单)。
补回归:坐席写内部备注 → 买家历史接口不含该条(条数与内容都断言),坐席端仍可见。

## B2 — 进程崩溃后 `running` 作业永久孤儿化(**持久性**)✅ 已修

### 实测(函数直调,构造崩溃-重启序列)

```
1) 入队 job=probe-job-…            状态='pending' attempts=0
2) 抢占(worker 取走,handler 执行中) 状态='running' attempts=1
3) 模拟崩溃:丢弃队列实例,handler 已执行次数=0
4) 重启后 run_once ×5 共处理 0 条
   该作业最终状态='running' attempts=1 last_error=None
   handler 累计执行次数=0
   队列统计={pending:0, running:1, done:0, dead:0}
>>> 作业永久停在 running、从未执行、也未进 dead-letter = True
```

### 根因:只写不读的状态

`STATUS_RUNNING` 在全仓**只被写入一次**([`jobs.py:372`](../backend/app/jobs.py:372) 抢占时),
**从未被任何查询用于回收**:
- `_claim_next` 只 `select(Job).where(Job.status == STATUS_PENDING)`;
- `start()` 只起线程,不扫残留;
- 全仓无 `stale` / `lease` / `heartbeat` / `reclaim` / `started_at <` 任何机制(已 grep 确认)。

所以只要进程在 handler 执行中死掉(崩溃、被 kill、部署重启、worker 线程异常退出后重建),
那条作业就**既不重试也不进 dead-letter**,永久悬空。

### 影响面

`lifespan` 里 `jobs.start_worker(engine)` 是**生产必需路径**
([`main.py:57-62`](../backend/app/main.py:57) 注释明写「生产必须走异步队列,否则 P95 被业务写锁拖累」),
而 [`api/chat.py:574`](../backend/app/api/chat.py:574) 的异步分支把**每轮对话**作为作业执行。
即:一次重启就可能让若干买家的那一轮请求永远没有结果,且监控上只看到 `running` 计数不降。

### 为什么测试没抓到

`tests/test_jobs.py` 12 条覆盖了消费/dead-letter/内联/优雅停/幂等停/统计/`run_once` 不死循环,
**没有一条构造「running 中途崩溃」**。

### 建议修法

启动时回收 + 运行期租约二选一(建议先做前者,成本低):
1. **启动回收**:`start()` 时把 `status='running'` 且 `started_at` 早于本次启动的行重置为
   `pending`(`attempts` 保留,超限则直接 `dead`)。单机单 worker 下安全。
2. **租约超时**:给 `running` 加 `lease_expires_at`,worker 定期把过期租约重置为 `pending`。
   多 worker 部署前必须做这一档。
补回归:构造 running 残留 → 新队列实例启动后该作业被重新消费或进 dead-letter。

## B3 — PII 占位符与用户字面文本撞号(**低:文本完整性**)✅ 已修

### 实测(函数直调)

```
原文   : 我的备用标记是[PHONE_1],真实号码13800138000
mask后 : 我的备用标记是[PHONE_1],真实号码[PHONE_1]
restore: 我的备用标记是13800138000,真实号码13800138000   ← 用户字面文本被改写
```
两号码场景同理:用户写 `[PHONE_2]` 字面量 + 两个真实号码 → 字面量被反解成第二个号码。

### 根因

[`pii.py`](../backend/app/pii.py) `_placeholder()` 按类型顺序分配 `[PHONE_n]`,
**不检查原文里是否已存在同形字面量**;`restore()` 用 `PII_PLACEHOLDER_RE` 全局替换,
无法区分「本轮分配的占位符」与「用户自己写的同形文本」。

### 影响边界(不夸大)

`PIIMasker` 是**每请求独立实例**,`mapping` 不跨轮不跨用户,
所以**不构成跨用户 PII 泄露**——被写进去的始终是**同一个用户自己**的号码。
属「静默改写用户原文」的健壮性问题,与上一轮 A3 同类。

### 建议修法

分配占位符时避开原文已出现的同形串(如改用不可能自然出现的分隔符,
或先扫描原文把已有 `[KIND_n]` 字面量登记为"保留",分配时跳号)。
补回归:原文含字面 `[PHONE_1]` + 真实号码 → restore 后字面量逐字保留。

## B5(假设)—— 确认门失败回退 + handoff 无幂等键 → 重复建单:**已否证,不成立**

留档是因为它是个**看起来很像缺陷**的组合,值得记下为什么不是。

### 怀疑的组合

- `_execute_confirmed` 失败时调 `_release_claim()` 把确认卡从 `confirmed` **退回 `pending`**,
  注释写「保留可重试」([`nodes.py:661`](../backend/app/graph/nodes.py:661));
- `handoff__create_ticket` 的九字段 **`idempotency_key=None`**(refund 有);
- [`tools/handoff.py`](../backend/app/tools/handoff.py) `execute()` **无任何去重查询**,
  无条件 `Ticket(...)` + `commit()`。

推论:若 `execute` 在 **commit 之后**才抛异常(如 `refresh`/`flush` 失败),
卡退回 pending,再 resume 一次就该建出第二张工单。

### 实测(`.tmp/audit_probe5.py`,走真实 `runner.run` / `runner.resume`)

把 `handoff.execute` 包成「先真建单并 commit,再抛异常」,然后连续 resume 两次:

```
1) 首轮 intent=handoff,拿到 handoff__create_ticket 确认卡,该会话工单数=0
2) 第一次 resume(approve) -> UNKNOWN_OUTCOME 话术;execute 调用=1,工单数=1
3) 第二次 resume(approve) -> 同样话术;        execute 调用=1,工单数=1
>>> 同一次人工确认产生 1 张工单(应为 1);重复建单 = False
```

### 为什么不成立(机制)

[`nodes.py:964`](../backend/app/graph/nodes.py:964) 的确认门条件是
`if confirm and not confirm.get("decided")`。第一次 resume 后 checkpoint 里已写
`confirm.decided=True, executed={ok:False,…}`,且该 thread **已无挂起 interrupt**;
第二次 `Command(resume=…)` 不再有中断可恢复,直接返回终态,**节点根本不会重跑**。
所以 DB 卡回到 pending 也不会被再次执行。

**结论:resume 幂等在「工具 commit 后故障」这一最坏时序下依然成立**,
`_release_claim` 的"可重试"只在 DB 层留了余地,图层面另有 checkpoint 兜底。

### 一条留观(未证实,不当结论)

上述时序下 **DB 卡状态(pending)与图状态(decided=True)不一致**。
同一 thread 内安全;若将来出现**绕过图、直接按 token 执行确认卡**的新路径,
这层不一致就可能变成真缺口。新增此类路径时必须补 handoff 的自然幂等
(按 `session_id` 查未关闭工单)或给它加幂等键。

## C1 — 引用卡把内部条款代号显示给买家(**信息卫生**)✅ 已修(方案①)

> 修完 B 系列后继续挖 `nodes.py` 剩余节点时发现的。与 B1 **同一个模式**:
> 后端脱敏了一条路径,另一条路径把同样的数据原样交出去。

### 实测(`.tmp/audit_probe6.py`,真实 `runner.run` + 真实政策库)

问「七天无理由退货的期限是多久?运费谁承担?」:

```
回复正文: '根据店铺政策:\n[1] 七天无理由退货运费承担(v1):…'
正文里是否残留内部代号: False        ← draft 已脱敏,符合 ISS-21

citations 共 3 条:
  index=1 clause_id='RP-02'
  index=2 clause_id='RP-11'
  index=3 clause_id='RP-01'
>>> 后端脱敏覆盖 draft 但漏掉 citations = True
```

**前端确实把它显示出来**([`frontend/app.js`](../frontend/app.js)):
```

402: "条款 " + (cite.clause_id || "—") + version            ← 引用卡元信息,直接可见

```

所以买家看到的是:正文写「七天无理由退货运费承担」(已脱敏的标题),
**紧下面的引用卡却写着「条款 RP-02 v1」**。

### 根因

`sanitize_customer_text` 的调用点只有三处:
[`nodes.py:1315`](../backend/app/graph/nodes.py:1315)(compose 的 draft)、
[`chat.py:594/596`](../backend/app/api/chat.py:594)(SSE delta)、
[`agent.py:721`](../backend/app/api/agent.py:721)(坐席建议回复)。
**`citations` 是响应里另一个字段**,由 [`runner._citations`](../backend/app/graph/runner.py:187)
原样透传 `clause_id`,从未过脱敏;前端又直接渲染它。

W13 ISS-21 的目标是「内部条款代号 `RP-xx`/`LP-xx` **禁止出现在买家可见文本里**」——
引用卡上的文字也是买家可见文本,这条没达成。

### 影响与定级

泄露的是**内部标识符**(条款编号),不是个人数据,所以比 B1 轻。
但它恰好是项目**明确立过规矩要防**的东西,且买家一眼就能看到,属"规矩没落实"。

### 修法口径(用户已裁定:方案①)

PRD §2 要求「答案 + `[n]` 条款号引用(可点回原文)」——`[n]` 是引用把手,
`RP-02` 是内部编号,两者不是一回事。当时列的三个选项:

1. **前端改显示标题**(推荐,✅ **用户选定**):引用卡元信息用 `cite.title`(需后端在 citations 里补 title),
   悬浮提示同理;`data-clause` 保留供内部定位(不进可见文本)。
2. **后端按角色裁剪**:买家侧 citations 不返 `clause_id`,只返 `index` + `title` + `snippet`;
   坐席侧保留代号。更彻底,但改响应契约,要同步前端与既有测试。**未采纳**。
3. 只把 `clause_id` 过一遍 `sanitize_customer_text`(代号→标题)——最小改动,
   但会让 `clause_id` 字段名与内容不符,不推荐。**未采纳**。
