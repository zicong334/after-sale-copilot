# 架构反思:从"测试全绿"到"业务正确"的四堂课

> 主会话亲笔,2026-11-09。素材全部来自本项目(售后 Copilot)两周实战的台账与验收记录,每条都有 commit/报告可溯源。
> 用途:项目复盘 + 简历/答辩的深度叙述素材。

## 课一:为什么"转人工"必须是物理静默,而不是一句礼貌话术

第一版实现照设计卡字面做了"转人工后返回固定话术、不再调 LLM",测试也按字面编码(`ai_replied=False` = 模型没跑),于是 334 个测试全绿地放过了一个产品级错误:用户视角里,"人工已接手"的横幅和 AI 继续吐字同时出现,每发一条消息还弹一次横幅——**系统一边宣称闭嘴一边喋喋不休**。用户手测一眼看穿,而我的验收没看穿,因为我的测试和实现共享了同一个字面理解。

修正后的语义是物理的:会话进入 `handed_off` 后,路由守卫不跑图、不调工具、**响应体里连 reply 字段都是空串**,用户消息只以 `author_type=user` 落进工单历史,前端只渲染一条系统级 ack。"AI 停止回复"从"模型没被调用"升级为"不存在任何 AI 文本产物"。

**教训**:验收断言要钉在**用户可观测的产物**上(响应体里有没有 AI 文本、横幅出现几次),而不是内部标志位(模型跑没跑)。内部标志全对,产品照样错。

## 课二:为什么必须依赖确定性护栏,而不是 prompt 约束大模型

第一轮真实模型评测(48 条 ×3)判"未达到":overall 0.6944、critical 6。失败簇高度集中——对抗输入下,模型**跳过工具调用、用泛化话术兜底**(查别人订单时不调 `shop__get_order` 做归属核验,直接编一句"没查到";注入场景误调退款工具)。这些不是知识缺口,是决策缺口;而决策缺口靠 prompt 里写"你必须先查订单"是治不住的,因为 prompt 是概率性的。

修复包没有试图让模型变聪明,而是给每个失败模式加一层**非 LLM 的代码守卫**:订单号形态出现而 trace 里没有核单调用→编排层强制注入核单;退款工具执行前查同 trace 的 `policy__check_return eligible` 证据,没有就 `BUSINESS_REJECT`;注入特征在感知层命中→图前拦截,固定安全话术;回复声称"已转接/查不到"而同轮无证据→确定性替换话术。第二轮:overall 0.9236、critical 0、对抗层 0.9524。

W6 的破坏性测试把这套哲学推到极端:10 线程并发确认(恰 1 次执行,靠 per-token 锁 + CAS)、SQL 级断言越权查询的 WHERE 必含 `customer_id` 绑定、过期确认卡重放零执行。**安全属性放在模型够不着的地方,才叫安全属性。**

**教训**:LLM 负责理解与表达,确定性代码负责事实与边界。分层不是架构洁癖,是故障隔离——概率层出错时,确定性层把爆炸半径圈死。

## 课三:CAS 与幂等键——退款并发 TOCTOU 的两道闸

归档旧代码的 `claim()` 是"先 SELECT 看状态、再 UPDATE 改状态",两个客服可同时领同一张单;退款链路没有幂等键,超时重试就是重复建单。新实现的两道闸:

1. **CAS(比较并交换)**:所有状态迁移是 `UPDATE … WHERE id=? AND status='旧状态'`,`rowcount==1` 才算成功,否则 409 并回读真实状态。读-判-写之间没有窗口,因为"判"被搬进了 WHERE。
2. **幂等键按目标状态生成**:`sha256(order_id | target_state | reason | amount_cents)`,数据库 UNIQUE 兜底;重复提交返回已有单 + `idempotent_hit=true`,而不是报错或新建。确认流再加 per-token 锁:10 线程并发确认同一 token,1 次真实执行 + 9 次幂等回执。

**教训**:锁防并发、幂等防重复生效,两者不互相替代。超时是"结果未知"而不是"失败",重试必须复用同一个幂等键,否则重试本身就是资损来源。

## 课四:"测试全绿 ≠ 业务正确"的三次实证

1. **W1-C 用例自相矛盾**:一条 golden 用例 context 无订单、文本是纯政策问题,expected_tools 却要求调用"必带订单参数"的判责工具——逻辑上不可满足。实现会话如实报 FAIL 不硬凑;修法归立法者(主会话):改期望、升评测集版本、留痕。用例是法,实现者不许改法,但法本身要有修订程序。
2. **W2-B pattern 拒真实数据**:`order_id` 的 schema pattern 照抄设计卡示例 `^ORD-…$`,而 seed 数据是 `seed-order-…`;30 个工具测试全绿,因为测试夹具自造了 ORD- 单号。是我的**实测演示**(用真实 seed 单号调一次)抓到的:越权路径卡在 SCHEMA_ERROR 而不是 NOT_FOUND_OR_FORBIDDEN。测试数据与生产数据不同源,绿的是幻觉。
3. **W5 前端状态误判**:380 个测试全绿、API 级真静默实测通过,但用户实机一点就死——`ticket` 无 session_id,前端按"该客户最近工单"取状态,历史关闭工单毒化新会话。测试绿在每一层局部,死在层与层之间的**状态归属假设**上。headless 浏览器真截图才让假设现形。

**教训**:绿是必要条件。验收必须包含至少一次"用真实数据、真实入口、用户视角"的端到端取证(演示脚本、真截图、真并发),并且断言写在业务产物上而非内部标志上。

## 附:评测先行的复利

W1 就写 10 条用例、W4 补到 48 条,每条 17 字段、断言业务结果。复利在三轮显现:FakeLLM 时代它是编排回归网(换图不倒退 10/10);第一轮真实评测它是诊断器(失败簇直接指出缺口类型);修复后它是裁判(0.6944→0.9236 的每个百分点都可归因)。评测集版本化(cs-eval-w1-…→cs-eval-v1-20261108b)让"改法"与"执法"分离——**没有 case 就没有失败归因,只有运气**。
