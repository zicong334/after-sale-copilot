### D5 为什么是 critical(以及它**不是**什么)

买家写一条 `is_internal=True` 的「内部备注:主管已口头批准本单全额退款,可直接打款,无需再核」,
坐席工作台会给它挂上**「内部」角标**(`frontend/agent.js:576`),
即**买家可控文本被渲染成坐席内部口径**。配合 D3(能读到真实内部备注的措辞),
攻击者可以先学口径再伪造。这是**信任边界击穿 + 社工诱导资损**。

**必须说清它不是什么**:它**没有**绕过确认门,也**没有**自动打款路径——
退款仍走 `refund__create` 确认卡 + 人工审核(PRD §4 红线未被击穿)。
伤害面是**误导人工决策**,不是机器自动执行。定 critical 是因为信任边界本身被打穿,
不是因为存在自动资损链。

## E 系列 — 语义缓存的「PII 永不缓存」只守了 query 一半(**high**)✅ 已修

第三轮的结论是「语义缓存覆盖扎实(22 条测试)」。本轮从**出口**看:
**缓存本身就是买家可见回复的一条出口**,而 `lookup()` **只有 merchant 维度、没有 customer 维度**
(`cache.py:563`)——同店所有买家共享。设计上的护栏是 `is_cacheable` 的「含 PII / 订单号永不缓存」。

### 实测一:函数直调(`.tmp/audit_probe8.py`)

```
--- E1 store 是否扫 payload 侧 ---
query='退货运费谁承担'(本身无 PII 无订单号)
reply='您的订单 seed-order-019 已发货,收货手机 13800138000,退货运费由买家承担。'
>>> E1 store 接受了带 PII/订单号的 reply = True

--- E2 另一次请求同 query ---
lookup(同 query,同商户,不带任何 customer 维度) -> 命中
取到的 reply = '您的订单 seed-order-019 已发货,收货手机 13800138000,…'
>>> E2 缓存把买家A的手机号/订单号交给了另一次请求 = True

--- E3 两处 PII 口径 ---
guardrails.PII_PATTERNS 类型数 = 3(手机/身份证/地址)
cache.PII_PATTERNS      条数 = 3(占位符/手机/身份证)——**没有地址**
guardrails 地址正则命中该 query = True
cache.is_cacheable('送到杭州市西湖区文一西路 100 号 3 单元 501 的快递能退吗') = True
>>> E3 含收货地址的 query 仍被判定可缓存 = True

对照1 query 含手机号 -> is_cacheable = False(应 False)✅
对照2 跨商户 lookup  -> 未命中(应未命中)✅
对照3 写意图 intent=refund -> store = False(应 False)✅
```

**根因**:`cache.py:648` `store()` 只调 `is_cacheable(text, intent=intent)`——

## F1 — 七天无理由的「签收天数」锚在**订单创建时间**上,误拒正当退货(**high**)✅ 已修

### 读码事实

- `nodes.py:1161`:`days = _days_since_delivery(context, order.get("created_at"))`
- `nodes.py:274` docstring 自认:「上下文显式值优先(评测用例给定时),**否则按订单创建时间推算**」
- `models/orders.py` `Order`:**只有 `created_at`,没有 `shipped_at` / `delivered_at`**
- `tools/policy.py:107`:RP-01 七天无理由 `max_days=7`,`:198` `days_since_delivery > 7` → 不可退

政策窗口从**签收**起算,而创建 ≤ 签收 ⇒ 用创建时间推算会**系统性高估**签收天数。
方向是**误拒**(不是误放),伤客户且违反政策口径。

### 实测(`.tmp/audit_probe10.py`,真实 runner 经 `/api/c/chat`)

订单 `status=delivered`(已签收),唯一变量是创建时间:

```
主案例:10 天前创建、今天签收(真实签收天数 = 0,应可退)
  intent=order_judge  工具链=['shop__get_order','policy__check_return']
  回复='已核对订单 seed-order-f1old(状态:已签收)。判定:已超 7 天期限,原则上不予受理。…'
  买家可见判定:误拒=True

对照1:2 天前创建、今天签收
  工具链=['shop__get_order','policy__check_return','refund__create']
  回复='…判定:符合七天无理由政策,可按流程为您办理。已生成退款申请确认卡…'
  受理=True

对照2:**同一张 10 天前创建的订单**,显式 context.days_since_delivery=0
  工具链=['shop__get_order','policy__check_return','refund__create']
  回复='…判定:符合七天无理由政策…已生成退款申请确认卡…'
  受理=True

>>> F1 用创建时间当签收天数,导致正当退货被误拒 = True
```

**对照2 是决定性的**:同一张订单,只把签收天数从「兜底推算」换成「显式给定」,
判定就从**误拒**翻成**受理** ⇒ 缺陷精确落在**兜底锚点**,判责规则本身没问题。

### 为什么测试没抓到

评测用例与单测**普遍显式给 `context.days_since_delivery`**(docstring 明说「评测用例给定时」),
于是**兜底分支从未被断言**。而生产链路里买家不会传这个字段——
**测试走的是一条生产永不走的路径**。这与 A1/B1 的「覆盖与暴露面不匹配」同构。

### 建议修法(**有产品口径要定**)

根因是**数据模型缺时间戳**,不是算错。两条路:

1. **补时间戳(推荐)**:`Order` 加 `delivered_at`(可空),`ship`/`deliver` 流转时写入;
   `_days_since_delivery` 优先 `delivered_at`,缺失时**不要静默用创建时间**——
   要么转人工核实,要么明确告知「以签收时间为准,需核实」。需一条 Alembic 迁移(第 11 条)。
2. **只改兜底行为(最小)**:无签收时间时**不臆断天数**,直接走人工核实分支。
   不动 schema,但买家体验多一次转人工。

⚠️ **不要**简单把兜底改成 `return 0`——那会把「超期」也一律放行,方向反过来变成资损。
补回归必须覆盖:创建久+签收近(应可退)、创建近+签收久(应拒)、无签收时间(按裁定口径)。

## G1 — 坐席建议的模型 prompt 入口不设内部备注门(**medium-high**)✅ 已修(选项二)

### 实测(`.tmp/audit_probe11.py`)

```

  **整体通过率不能只看总分,要看分项**。

### 建议修法(**改评测口径需用户裁定**)

1. `expected_numbers` 改成**带单位/上下文**的期望(如 `"7 天"` / `"15 元"` / `"11900 分"`),

2. 兼容中文数字(「十五天」)以免假阴性;
3. ⚠️ **这会改变历史评测口径**:改完必须**重跑基线**并说明「与旧报告不可直接比」。
   真实 R3 重跑**花真实 API 钱,需用户批准**;FakeLLM 基线重跑不花钱,可先做。
4. 建议**先只加重算脚本、不改 cases_v1.json**,用「旧口径 vs 新口径」双跑对照,

### 方法论:换打法立刻见效

第三轮末尾写的建议是「把**枚举一份数据的所有出口、逐个核对守卫**当固定检查项」。

 `cache.PII_PATTERNS` vs `guardrails.PII_PATTERNS`(地址)、
