## 0. 结论前置

1. **「SQLite 单写者是结构性瓶颈」这个假设成立,而且比原判断更严重 —— 写路径是负伸缩。**
   并发 1→2,写吞吐从 **24.6 → 11.6 rps(掉 53%)**;同期读吞吐 362.6 → 394.1 rps(升)。
   加并发让写**比串行更慢**,这不是"排队变长",是锁竞争 + 回滚重试的净损耗。
2. **写路径 P99 在并发 4 时炸到 4.5 秒**(c1 是 98.7ms,**46 倍**),而读路径 P99 始终 ≤37ms。
   并发 4 时读写吞吐相差 **40.6 倍**。
3. **压测抓到一个 831 条功能测试从未覆盖的真缺陷**:并发写下抛**未处理 500
   `sqlite3.OperationalError: database is locked`**(见 §4)。全部功能测试都是单线程,所以从未触发。
4. **平均值会骗人**:写 c4 的 mean=321ms 而 P99=4547ms,**差 14 倍**。
   只报平均值的性能报告在这个系统上会得出完全错误的结论。

## 4. 压测抓到的真缺陷(新增 R16,P1)

### 现象
写 c8 出现 1 次 **HTTP 500**,错误率 0.41%。服务日志里两处完整 traceback。

### 根因(已定位到行)
```
app/api/chat.py:451  chat
app/api/chat.py:209  _run_turn
app/api/chat.py:765  _resolve_session
[SQL: INSERT INTO chat_session (id, merchant_id, customer_id, status, ...)]
sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) database is locked
```

- `app/db.py:_attach_sqlite_pragmas` **只设 `foreign_keys=ON` + `journal_mode=WAL`**,
  **没有显式 `busy_timeout`**;`create_db_engine` 的 `connect_args` 也**没有 `timeout`**
  → 走 pysqlite 默认 **5s**。这与实测 P99≈4.5s / max≈5.5s **正好吻合**:
  请求在写锁上排队接近 5s,超时后抛错。
- **全仓 `backend/app` 搜不到任何 `OperationalError` / `database is locked` / `busy_timeout` 处理**
  → 锁竞争直接变成**裸 500**。

### 为什么这是缺陷而不只是"SQLite 就这样"
1. **500 会招致客户端与网关重试** → 在已经饱和的写路径上放大流量(参考判据:限流/过载禁止返 5xx)。
   正确形态是**受控降级**:503 + `Retry-After`,或有界重试后失败。
2. **无有界重试**:瞬时锁竞争本可重试一次即成功,现在直接失败。
3. **与迁 PG 无关**:PG 上同样会有序列化失败/死锁,也需要这层处理。**这条现在就该修**。
4. **831 条功能测试全是单线程**,所以这个面**从未被覆盖** ——
   又一次「测试全绿 ≠ 业务正确」,与 A1/B1/C1 同构。

### 建议动作
| 层 | 动作 | 成本 |
|---|---|---|
| 存储 | 显式设 `busy_timeout`(与接口超时对齐,**取值需按 SLO 定,本轮不拍数字**) | 0.2 人日 |
| 应用 | 锁类 `OperationalError` → **503 + Retry-After**,禁止 500 | 0.5-1 人日 |
| 测试 | 补**并发写回归**,断言不出现裸 500 | 0.5 人日 |

⚠️ **不要靠调大 busy_timeout 掩盖问题**:那只是把失败变成更长的等待,P99 会更差。
真正的解锁项是**迁 PG**(见 §5)。

### ✅ R16 已修(2026-11-21,同日)

**修法更正**:初稿写的「有界重试(≤2 次短退避)」**已撤回**。
reference 明写「**非幂等操作禁止自动重试**」——对话 POST 可能已有工具自行 commit,
整请求重放会双写。所以只做**受控降级 + 可观测**,重试交给持幂等键的调用方。
这是对自己初稿措辞的更正,不是缩水。

落地(`app/errors.py`,新增第 7 个 handler,总数 8→9):
- `is_storage_busy(exc)`:只认 `OperationalError` 且文本含
  `database is locked` / `database table is locked` / `database is busy` /
  `could not serialize access` / `deadlock detected`(**含 PG 序列化失败与死锁**,迁 PG 后同样生效);
- 命中 → **503 `STORAGE_BUSY` + `retryable=true` + `Retry-After: 1`**;
- **非锁类**(schema 错 / 磁盘 I/O 错)**仍走 500** —— 把 bug 伪装成"稍后重试"会掩盖真问题;
- 错误体不泄露 SQL 与堆栈(与既有兜底同口径)。

**TDD**:新增 `tests/test_storage_busy.py` **13 条**。
RED **7 failed / 6 passed**(失败的是锁分类 5 条 + 503 + Retry-After;
非锁分类与"schema 错仍 500"先就通过)→ GREEN **13 passed**。
真实锁竞争的复现依赖时序,单进程测试里不稳定,所以用**确定性注入**测处理逻辑,
真实并发证据由压测复跑提供(下)。

**压测复跑验证(真实路径,不是单测)**:

| 口径 | 修前 | 修后 |
|---|---|---|
| 写 c8 失败 kinds | `{"status:500": 1}` | **`{"status:503": 2}`** |
| 写 c16(加压新档) | — | **`{"status:503": 23}`**,错误率 8.88% |
| 裸 500 | 有 | **零** |

→ **受控降级在真实并发路径上生效**,不只是单测里成立。
同时 c16 吞吐进一步掉到 11.9 rps,**负伸缩继续**,说明系统早已过饱和点 ——
再次印证「加并发不是解锁项」。原始数据 `.tmp/load_write_after_r16.json`。

⚠️ **仍未做**:显式 `busy_timeout`(取值需 SLO,本轮不拍)、
真实并发压力的**常驻回归**(需 CI 里跑短阶梯,待 service container 接通)。

## 5. 对容量公式的输入:现在有了什么、还缺什么

```
N = ceil(Q_peak × k / Q_single_safe)
```

| 输入 | 状态 |
|---|---|
| `Q_single_safe`(单机安全 QPS) | **有了框架侧的候选值,但还不能定**:写路径在 c1 就已经是吞吐峰值(24.6 rps),c2 起负伸缩。若以"P99 不超过某 SLO"为安全水位,**需要先有 SLO**才能取点。**本轮不拍这个数** |
| `Q_peak`(峰值 QPS) | **仍缺**(用户明确没有目标) |
| `k`(安全系数) | 经验区间 1.3–1.5,**待压测校准** |
| SLO(P99 / 错误率预算) | **仍缺** |
| 真模型延迟 | **未测**(裁定暂不跑) |
| PG 上的曲线 | **未测**(本机无 PG;待 CI service container) |

**能确定的结构性结论(不需要上面任何缺失项)**:
> 在 SQLite 形态下,**提高并发不能提高写吞吐**(实测负伸缩);
> 因此**加实例 / 加并发都不是解锁项,迁 PG 才是**。
> 评审报告 §0 的「先 PG → 再 Redis → 才多实例」顺序,**现在有实测数据支撑**,不再是读码推断。

## 7. 复现命令

```bash

.venv/Scripts/python .tmp/load_server.py
# 2) 写/读双阶梯
.venv/Scripts/python backend/scripts/load_probe.py --scenario write \
    --concurrency 1,2,4,8 --duration 15 --warmup 3 --out .tmp/load_write.json
.venv/Scripts/python backend/scripts/load_probe.py --scenario read \
    --concurrency 1,2,4,8 --duration 15 --warmup 3 --out .tmp/load_read.json
```

不是出具正式容量报告;正式容量结论需长稳态 + 真实数据量 + SLO,届时重跑。
