## 2. 跑之前必须先解决的前置

1. **PG 驱动不在锁文件里**。`requirements.lock.txt` **不含 `psycopg`**。
   `verify_runtime.sh pg` 的测试阶段会因缺驱动失败 —— 需先决定装 `psycopg[binary]` 到
   dev 依赖还是进生产锁(**进生产锁意味着镜像体积与依赖面变化,属选型决策**)。
   ⚠️ 脚本里已就此写了注释,**没有偷偷替你装**。
2. **CI 从未跑过**。仓库无 remote,`ci.yml` 自己的注释就写着"推送后才真正生效"。
   要走 service container 路线,得先决定**是否把仓库推到 GitHub**(发布动作,需用户授权;
   仓内有 seed 演示账号、政策语料、审计报告引用的内部口径)。
3. **PG 端口与凭据**。脚本默认 `postgresql+psycopg://copilot:copilot@127.0.0.1:5432/copilot`,
   与 compose 的 `${POSTGRES_USER:-copilot}` 默认值对齐;若改过 env 需同步传 `PG_URL`。
4. **Alembic 在 PG 上的 batch 模式**。0011 的 downgrade 用 `batch_alter_table`
   (为兼容 SQLite 的 DROP COLUMN)。PG 原生支持 DROP COLUMN,batch 会走重建表路径 ——
   **能跑但没必要**,PG 上可考虑按方言分支;这属于跑通后的优化,不是先决条件。

用户在修正顺序里明确要求:**把 Redis 三项实现写出来,带「未运行时验证」标记**。
所以本轮**会实现**,不是推后。但必须把"测到了什么、没测到什么"划清:

**能在本机真测的(会写成测试)**:
- 限流键构造、两维( subject / tenant )口径、`Retry-After` 语义;
- 令牌桶参数换算、**fail-open / fail-close 按接口分档**的决策逻辑;
- L2 键前缀、失效广播的频道划分、L1 回填与版本比较逻辑;
- Redis 不可用时**降级回进程内实现**的路径(这条本机能真验)。

**本机测不到、必须等容器的(标记为未运行时验证)**:
- **集群总放行量 ≈ 阈值而非 N×**(要两个真进程 + 真 Redis);
- `INCR+EXPIRE` 是否真的让 `_buckets` 无界增长消失(要真 Redis 的 TTL 行为);
- 跨实例 Pub/Sub 失效延迟、L1/L2 版本差(要两个实例);
- Lua 脚本的**真原子性**(本机只能用单进程模拟,证明不了并发原子)。

⚠️ **纪律**:不得用"我调用了 Redis 客户端"的 mock 断言冒充上面这些结论 ——
那正是评审批评的「测试 mock 行为而不是真实行为」。
本机测试只断言**我自己写的逻辑**,Redis 侧语义一律留到 `verify_runtime.sh` 清标记。

## 6. 三项「待定」的裁定归属与解锁条件(2026-11-21 用户拍板:标注,不拍数字)

用户明确:这三项**决策权不在执行方**(合规 / 运维 / 真模型压测),
能力已做好、默认值保守,**正确做法是文档标注,不是硬编一个数**。

### 6.1 审计留存天数 —— 待**业务/合规**裁定

- **能力已实现**:`jobs.purge_turn_audit()` + `TURN_AUDIT_RETENTION_DAYS`,**默认关闭**(未设则一行不删)。
- **参考值 90 天,仅为示例,非合规结论**。实际留存期需业务/合规方裁定后配置。
- 为什么不默认开:保留期属合规决策(等保/GDPR/行业监管各不相同),
  **没拍板前自动删审计行是破坏性且不可逆的**。
- 为什么不脱敏代替:审计定位是"事后可查实际说了什么",涂掉内容会摧毁审计价值。
- **解锁条件**:合规方给出保留期 → 设 `TURN_AUDIT_RETENTION_DAYS=<天数>` → 挂定时调用。
  非法值与 0/负数会**显式报错**(0 会删光审计)。

### 6.2 告警阈值与通知渠道 —— 待**运维**签认

- **规则已写**:`deploy/alerts.yml` 两条(最老死信 >1h、dead 计数 >10),
  **1h / 10 条为起步值,待运维签认**,不是 SLO。
- **当前 compose observability profile 无 Alertmanager**:
  规则**仅在 Prometheus UI 可见,不发通知**。
- **用户裁定:不装 Alertmanager** —— 无专职运维时多一个组件是负担。
  通知渠道需另加 Alertmanager + receivers,**属运维决策**,不在本轮。
- **解锁条件**:有值班人与通知渠道后,再决定阈值与是否引入 Alertmanager。
  在此之前,死信靠 `/metrics` 的 `copilot_job_dead_oldest_age_seconds` **人工巡检**。

### 6.3 grace 的真模型口径 —— 待**真模型压测**校准

- **当前 30s** 基于 **FakeLLM 框架侧** max 5612ms × 1.2 ≈ 6.7s 推导,取 30s 留余量。
- **真模型 P99 未测**(用户裁定暂不跑真模型探针)。
- **口径公式**:`grace ≥ 真模型 P99 × 1.2`,**待真模型压测后重算**。
- 配套约束:entrypoint 的 `--timeout-graceful-shutdown 20` **必须小于** compose 的
  `stop_grace_period 30s`,否则 grace 白设。改 grace 时两者要一起调。
- **解锁条件**:批准真模型压测 → 拿到真模型 P99 → 按公式重算 grace 与内层超时。
