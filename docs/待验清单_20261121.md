### 8.5 nginx 路由缺口(container job 首轮的唯一失败,已修)

**怎么发现的**:新加的 container job 真 build 本项目镜像 + `compose up backend nginx`,
经 nginx 冒烟。前三步(静态页 / liveness / readiness)全 200,第四步 `POST /auth/login` **404**:

```
{"ok":true,"status":"healthy"} <- liveness
{"ok":true,"status":"ready"} <- readiness
curl: (22) The requested URL returned error: 404
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

**根因**:应用 OpenAPI 有 **51 条路径、8 个顶层段**(`/api /auth /health /healthz /orders /refunds /tickets /v1`),
而 `deploy/nginx.conf` 只有 `/` `= /metrics` `/health` `/healthz/ready` `/api/` `/ws/` 六个 location。
`/auth` `/orders` `/refunds` `/tickets` `/v1` **全部落进静态 `location /`(`try_files … =404`)**。
按真实路径逐条算,共 **19 个端点**在部署栈上不可用 —— 含登录、订单列表/详情/发货/签收/支付、
退款申请/审批/打款/驳回、工单全部读写。**不是"少一个接口",是整个部署栈不可用。**
**前端 UI 同样坏**:`frontend/agent.js:79` 调 `/auth/me` 校验登录态、`:529` 调 `/orders/{id}`、
`:542` 调 `/tickets/{id}`,经 nginx 全 404。开发态 uvicorn 直连不受影响,所以本机测不出来。

**为什么四轮审计 + 静态 lint 都没抓到**:
- 静态 lint 查的是"键齐不齐"(有没有 `proxy_pass`、`/metrics` 有没有 allow/deny),**不查覆盖完整性**;
- 全部 API 测试用 `TestClient` **直连 app**,根本不经过 nginx;
- 这正是「同一份数据/请求的不同出口没过同一道守卫」的又一例 —— 出口是**反向代理层**,此前从未被枚举。

**修法**(不硬编码前缀清单,否则新增 router 又会漏):
1. nginx 补五个 location。⚠️ **不能带尾斜杠**:`GET /orders` `/refunds` `/tickets` 是裸路径,
   写 `/orders/` 仍 404;而去掉尾斜杠有误吞同名静态文件的风险(前端 `api.js` 正是 `/api/` 必须带斜杠的原因),
   已核对 `frontend/` 现有 8 个文件无这五个前缀者。
2. `test_deploy_artifacts.py` 加**两条永久守卫**(先红后绿,红时精确列出 19 条):
   - `test_nginx_proxies_every_openapi_path_instead_of_serving_static`:
     从 `app.openapi()` 取**全部真实路径**,按 nginx 匹配语义(精确 `=` 优先,否则最长前缀)
     算出每条路径命中的 location,断言它必须 `proxy_pass`;
   - `test_nginx_static_frontend_files_are_not_swallowed_by_proxy`:**反向守卫**,
     枚举 `frontend/` 全部文件断言仍由静态 handler 提供,防止这次修复反过来打断前端。
     内含**门禁有效性自检**:合成一个去掉尾斜杠的 `/api` 前缀,确认匹配器真会把 `api.js` 判给它
     (本项目红线:假门禁比没门禁更糟)。

**顺带修掉的验证脚本自身缺陷**:`verify_runtime.sh` 原先 curl 80(nginx 实际映射 8080)、

### 8.7 优雅停机那步的**假验证问题**(自查发现,已加强)

上面 `停机耗时 0s,退出码 0` 看着是绿的,但**它证明的东西比声称的少**:
停机那一刻栈里没有任何在飞的长连接,所以"0 秒干净退出"只说明**进程响应了 SIGTERM 且没被强杀**,
**完全没触及** R11 真正声称的「grace 期内把 WS/SSE 长连接排空」。
按本项目红线(**假门禁比没门禁更糟**),不能拿这条清标记。

**加强后的检查**(同一 job,替换原步骤):
1. 登录 → 一轮对话拿 `session_id`;
2. 经 nginx 建一条真 WS(`ws://127.0.0.1:8080/ws/buyer/{sid}?token=…`)并**挂住不收**;
3. **在 WS 挂着的时候** `docker stop`,同时读该连接;
4. 断言两件事:**退出码 ≠ 137**(没被 SIGKILL)**且客户端收到带 `code` 的正常关闭帧**
   (而不是 TCP 被直接掐断)。后者才是"优雅"的可观测信号。
5. 输出 `stop_seconds` / `exit_code` / `ws_close` 三个字段,便于判断 grace 是否真在等。

⚠️ 若加强后**失败**(例如 uvicorn 只掐 TCP 不发关闭帧),那是**真发现**,
要如实记为缺陷并修,**不许把断言放宽回去**。

**连带修掉一个 lint 自身的静默失效**:停机步骤从 shell `docker stop "$CID"` 改成 Python
`create_subprocess_exec("docker","stop",cid)` 后,`check_ci` 原先拿 `yaml.safe_dump` 的结果做字面匹配,
而 **dump 会把 `"` 转义成 `\"`**,于是 `"docker", "stop"` 变成 `docker\", \"stop\"`,检查**静默失效**。
改为读 **step 的原始 `run` 文本**(`job_runs()`),并加用例覆盖两种写法。
这是「假门禁」的又一实例:**门禁自己也要有负控**。
