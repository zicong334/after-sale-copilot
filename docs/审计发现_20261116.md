## A1 — 根路径业务接口无角色校验,买家可自助退全款(**critical:越权 + 资损**)✅ 已修

### 实测结果(enforce 生产模式,真实 JWT,真实 HTTP)

用 `buyer_demo` 登录拿 **buyer** token(role=buyer, customer=`seed-cust-001`),全程只用这一个 token:

| 步 | 请求 | 结果 |
|---|---|---|
| 1 | `POST /orders/seed-order-013/deliver` | **200** — 该订单属于 **`seed-cust-003`**(别人),被推成 `delivered` |
| 2 | `POST /refunds`(全额 11200 分,reason=物流破损) | **201** — 给别人的订单建了退款单 |
| 3 | `POST /refunds/{id}/approve`,`decided_by="buyer_demo"` | **200** — 自己审核,状态 → `审核` |
| 4 | `POST /refunds/{id}/refund` | **200** — 状态 → `退款` |

**DB 回读**:退款单 `status='退款'`、`decided_by='buyer_demo'`、订单 `status='refunded'`。

另一条独立链(同一 buyer token):

| 步 | 请求 | 结果 |
|---|---|---|
| 1 | `POST /tickets/seed-ticket-001/claim`,`service_id="seed-agent-1"` | **200** → `claimed` |
| 2 | `POST /tickets/seed-ticket-001/close` | **200** → `closed` |

**DB 回读**:工单 `status='closed'`、`claimed_by='seed-agent-1'`(**买家冒充坐席**)。

### 根因(两层叠加)

1. **认证扩了,授权没扩**。`security.required_role()` 在 W13-ISS-60 改成白名单式:
   非公开路径一律 `ROLE_ANY`(强制 Bearer + 限流)。所以 `/orders`、`/tickets`、`/refunds`
   **需要登录,但任何角色都行**——`ROLE_PREFIXES` 只给 `/api/c/*`→buyer、`/api/b/*`+`/api/kb/*`→agent。
2. **这三组 router 内部只校验租户,不校验角色**。
   [`api/refunds.py:85`](../backend/app/api/refunds.py:85)、[:104`](../backend/app/api/refunds.py:104)、[:122`](../backend/app/api/refunds.py:122)
   都只调 `_assert_tenant(identity, refund)`,而它只比 `merchant_id`;
   [`api/orders.py`](../backend/app/api/orders.py) 的 `pay/ship/deliver`、
   [`api/tickets.py`](../backend/app/api/tickets.py) 的 `claim/close/status` 同样。
   项目**已有** `require_agent` 辅助函数,但只用在 [`api/kb.py:65`](../backend/app/api/kb.py:65)。

附带两个放大因素:
- `decided_by`(审核人)与 `service_id`(领单坐席)**都是客户端自填**,审计字段可任意伪造。
- `_assert_tenant` 只比租户、**不比 customer**,所以同店内买家能操作**其他买家**的订单/工单。
  读路径有隔离(`GET /orders` 对 buyer 过滤 `customer_id`),**写路径没有**。

### 影响

直接击穿产品第一红线。PRD §4 危险动作清单写的是「退款永远只是**创建申请单 + 人工审核**,
永不自动打款」;对话链路确实有确认门挡住,但 **REST 直调完全绕过**,买家自己就能走完
「推签收 → 建单 → 审核 → 打款完成」,还能拿别人的订单走。

agent 打 `/api/c/handoff/tickets` → 403。**根路径的 `/orders` `/tickets` `/refunds`
从未做过角色断言**;全仓也搜不到「买家不能 approve / refund / deliver / claim」这类用例。

## A2 — 非 `delivered` 订单退全款会卡死并回滚(**功能缺陷**)✅ 已修

### 实测结果

订单 `seed-order-013`,`status='shipped'`,实付 11200 分。用**坐席** token:

| 步 | 请求 | 结果 |
|---|---|---|
| 1 | `POST /refunds`(全额,reason=**物流破损**) | **201** |
| 2 | `POST /refunds/{id}/approve` | **200** → `审核` |
| 3 | `POST /refunds/{id}/refund` | **409** `STATE_CONFLICT`「订单退款完成失败: 需 delivered 且存在 status='退款' 的退款单」,param=`shipped` |

**DB 回读**:退款单停在 `审核`,订单仍 `shipped`。**这笔退款再也无法完成。**

### 根因

- 建单侧不设门槛:[`services/refunds.py:192`](../backend/app/services/refunds.py:192)
  `create_refund_request` 只查订单存在性与金额残额,**不看 `order.status`**;
  REST [`api/refunds.py:45`](../backend/app/api/refunds.py:45) 直接调它。
  (工具层 [`tools/refund.py:168`](../backend/app/tools/refund.py:168) 有
  `REFUNDABLE_STATUSES={"delivered"}` 门槛,所以**对话链路进不来,REST 能进来**。)
- 完成侧要求 `delivered`:[`services/orders.py`](../backend/app/services/orders.py)
  `refund_complete` 守卫 `Order.status == "delivered"`,不满足就 `session.rollback()` + 抛错。
- 而 [`services/refunds.py:367`](../backend/app/services/refunds.py:367) 在残额归零时**必须**调它:
  ```python
  if residual_amount(session, refund.order_id) <= 0:
      refund_complete(session, refund.order_id)   # 失败 → rollback 把退款单自身的状态更新也回滚掉
  ```
  所以失败不只是「订单没联动」,而是**连退款单置 `退款` 都被回滚**。

### 两个加重情节

- **`物流破损` 是 schema 明确允许的退款原因**(`RefundCreate.reason` 枚举),
  而物流破损天然发生在 `shipped` 阶段 → 这是**现实场景,不是构造出来的边角**。
- **部分退款反而能成**:残额 > 0 时走 `session.commit()` 正常返回;
  只有「最后一笔把残额退到 0」才炸。同一订单行为不一致,更难排查。

### 修法与验证(已实施)

**门加在 REST 入口,不是服务层**——这一点与原建议不同,理由是实测出来的:
`tests/test_services.py` 的订单夹具默认 `status="created"`,有 8 处服务层退款单测
建在上面(它们只测金额折算与幂等,不关心订单状态)。若把门加进
`create_refund_request`,会一次性打断这 8 条,迫使改一堆与政策无关的单元测试。

**分层结论**:服务层是**机制**(金额/幂等/守卫式迁移),入口才是**政策**落点。
工具层 [`tools/refund.py:168`](../backend/app/tools/refund.py:168) 本来就在入口拦,
现在 REST 入口 [`api/refunds.py`](../backend/app/api/refunds.py) 补上同一道门,
**复用 `tools/refund.REFUNDABLE_STATUSES` 常量**保持单一事实源(不新增第三份拷贝)。

新增 `_assert_refundable(order)`:非可退状态 → `409 STATE_CONFLICT`
「订单状态 X 不支持退款(仅已签收订单可退)」,**在建单前拒绝,不留脏单**。
该门与鉴权模式无关(internal 也生效),因为它是业务政策不是权限。

**回归**:`tests/test_fulfillment.py` 新增 2 条(拒绝 + 正向 delivered 仍可建单)。
RED 时 shipped 订单被建单 201(应 409),修完转绿。
**原始探针复验**:shipped 订单建单**第一步即 409**,不再产生卡死的退款单。

### ⚠️ 一处存量测试夹具修正(断言未放宽,单独留痕)

`tests/test_api.py::test_refund_amount_exceeds_paid` 原用 **`paid`** 状态订单测
「金额 10001 > 实付 10000 → 422」。新门会先返回 409,掩盖该用例真正要测的金额上限。
处置:夹具 `paid` → **`delivered`**,**断言一字未改**(仍 `422` + `AMOUNT_EXCEEDS_PAID`,
金额仍 10001 > 10000)。理由写进了用例注释。

这是本轮**唯一**改动存量测试的地方,且只动夹具不动断言。若你认为
「不可退状态 + 超额金额」应当优先报 422 而非 409,那是另一个口径裁决,可回退此处。

## A3 — 反编造护栏逐句重写会丢字符与段落换行(**低:文本完整性**)✅ 已修

### 实测结果(函数直调,无证据场景)

| 输入 | 输出 | 丢了什么 |
|---|---|---|
| `'。已为您退款。'` | `'我尚未执行退款操作;…'` | 句首 `。` |
| `'已退款。？'` | 同上 | 句尾 `？` |
| `'？？已转人工！！'` | `'我尚未为您转接人工;…'` | `？？` 与 `！！` |
| `'已退款\n\n好的'` | `'我尚未执行退款操作;…办理。好的'` | **`\n\n` 段落换行**(两段被粘成一段) |
| `'（已退款）'` | `'我尚未执行退款操作;…'` | 括号(**这一行原先归因过度,见下**) |

**写测试时的两条自我更正**:

1. **括号与被替换句自带的那个句末标点,属于「命中句本身」**,随整句被替换是预期行为,
   **不是正则漏字符**。上表最后一行原先把它也算成缺陷,属过度归因,已在此更正;
   对应的测试期望也已改成真正的不变量(只断言未被任何 match 覆盖的字符)。
2. **缺陷比原判更严重**:原以为只在"触发替换"时丢字符,实测发现
   **即使有证据、一条都不替换,函数也在改文本**——
   `'？？已为您退款！！\n\n感谢耐心等待。'` → `'已为您退款感谢耐心等待。'`。
   因为它对每条回复都做 `findall` + `join` 重组。这条由新增的
   `test_audit_status_claims_keeps_evidenced_text_byte_identical` 抓住。

### 根因

[`guardrails.py:385`](../backend/app/guardrails.py:385)
```python
_SENTENCE_RE = re.compile(r"[^。！？\n]+[。！？]?")
```
`findall` 只抓「一串非句读字符 + 最多一个句末标点」。**句首标点、连续标点、换行符
都不被任何 match 覆盖**,`"".join(out)` 重组时就静默丢弃。

### 影响

不涉及安全,但 `audit_status_claims` 跑在**每条回复**上,一旦触发替换就会悄悄改写
买家可见文本的排版(最明显是多段回复被粘成一段)。属「静默改数据」类小债。

### 修法与验证(已实施)

[`guardrails.py`](../backend/app/guardrails.py) `audit_status_claims` 由
`findall` + `"".join` 改为 **`finditer` + 把 match 之间的空隙原样拷回**:
每轮先 `out.append(body[cursor:match.start()])` 保留空隙,末尾再补 `body[cursor:]`。
替换判定与"同类连续句只替一次"的去重逻辑**完全不变**,只是不再吞掉未覆盖字符。

**回归**:`tests/test_guardrails.py` 新增 2 条——
`test_audit_status_claims_preserves_unmatched_characters`(句首标点/段落换行/连续标点必须保留)
与 `test_audit_status_claims_keeps_evidenced_text_byte_identical`(有证据时整段逐字不变)。
RED 两条皆红,修完 `test_guardrails.py` + `test_w13_guardrails.py` **49 条全绿**。
