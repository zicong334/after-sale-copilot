# 企业工程评审:售后 Copilot(2026-11-21)

> 用 `enterprise-engineering-design` skill 跑的第一轮架构评审。
> **评审基准(用户已拍板)**:作品集/教学加固 —— 按「假设要上生产」的通用判据审,
> **不代入本系统算容量数字**;允许引入 **PG + Redis**(不含 MQ);
> 部署目标 **docker-compose 单机、无专职中间件运维**;**无目标 QPS/SLA**。

## 0. 结论前置

**这个项目的功能正确性防线很硬(831 用例、四轮审计、确定性护栏、确认门),
但「上生产」这条轴上几乎是空白:零压测、零覆盖率门禁、容器与 PG/Redis 运行时从未验证。**

**最重要的一条结构性判断(不依赖任何流量数字)**:

> **当前形态下横向扩容是无效动作,而且会引入新缺陷。**
> 三个原因互相咬合:
> ① **SQLite 单写者**是结构性写瓶颈,而每轮对话都要写消息/审计/作业行 —— 加实例不解锁写吞吐;
> ② **限流是进程内计数器**,加实例后集群实际放行 = N × 阈值,阈值形同虚设;
> ③ **语义缓存与作业队列都是进程内**,加实例后缓存各自一份(一致性窗口 = TTL 30min)、
>    而 B2 的启动全量回收会**抢走别进程正在执行的作业**。
>
> 所以正确顺序是 **先 PG → 再 Redis(共享限流 + L2 缓存)→ 才谈多实例**,
> 反过来做会同时踩三个坑。这条顺序判断不需要 QPS 就成立。

## 4. 分块优化建议(问题 → 方案 → 权衡 → 落地成本)

### P0-1 建立性能基准(R1)

- **问题**:所有"性能"数字都来自功能评测。FakeLLM 单并发跑 144 次的 p95,与"多用户并发下的 P99"是**两个完全不同的量**,不能互相外推。
- **方案**:阶梯压测,**先压写路径**。判据:
  - 当只压政策问答(读多)→ 结论无效,因为 **SQLite 单写者**才是瓶颈,而每轮对话都写消息/审计/作业行;
  - 当压测覆盖「对话落库 + 入队 + 队列消费」→ 才能看到真实拐点。
  - 阶梯 10%→50%→100%→120% 目标负载,每阶 5-10min,预热 5min,稳态 ≥30min(**经验值,待压测校准**)。
  - 指标必须含 **P95/P99/P999 + 错误率 + 吞吐 + 并发 + 稳态时长**;错误率**必须把 429 与超时计入失败**(否则是口径作弊)。
  - SSE 单独测**首字节延迟**,不是总耗时。
- **权衡**:FakeLLM 档压测只能测**框架与 DB 开销**,不含真实模型延迟;真模型档要花 API 钱(用户已裁定暂不跑)。所以先出「框架侧容量曲线」,真模型侧标为待补。
- **落地成本**:压测脚本 + 阶梯执行 + 报告 ≈ **2-3 人日**。验证方式:压测报告本身 + 拐点对应的资源水位。

### P0-2 增量覆盖率门禁(R2)

- **问题**:这个项目**用三次真实事故证明了**用例数不等于覆盖:762 全绿时存在 critical 越权;B1 的 `is_internal` 断言测的是另一个端点;C1 的 citations 路径从未被断言。**用例数是投入指标,覆盖率是覆盖指标,两者不能互替**。
- **方案**:CI 加 `pytest --cov --cov-report=xml` + diff-cover 门禁,PR 强制 diff line ≥80% / diff branch ≥70%(**经验值**),豁免走书面审批。核心域(退款/权限/护栏)阈值上调,边缘模块分档。
- **权衡**:全量 831 用例已跑 25 分钟,加覆盖率会再增开销;CI 总时长判据是 ≤30min,**可能触顶**。对策:PR 只跑受影响子集 + 增量覆盖率,全量放夜间。
- **落地成本**:≈ **1-1.5 人日**。验证方式:故意提一个缺测试的 PR,确认被阻断。

### P0-3 容器与 PG 运行时打通(R3)

- **问题**:交付物齐备但**从未运行**。这不是"文档缺口",是**未验证的交付**。
- **方案**:在有 Docker 的机器上:①`compose up` 最小栈 + 冒烟;②`--profile full` 起 PG/Redis;③跑 Alembic 到 head 验证 11 条迁移在 PG 上的方言;④`--profile observability` 验证 Prometheus 真能抓到 `/metrics`。
- **权衡**:PG 方言适配(W12-4)是**真工作量**,不是跑一遍就完;SQLite 专有写法(如 `PRAGMA`、部分唯一索引语义)需逐条核。
- **落地成本**:跑通 + 冒烟 ≈ **0.5 人日**;**PG 方言适配另计 ≈ 2-4 人日**(待逐条盘点后收敛)。验证方式:compose 冒烟 + 迁移 up/down 双向。

### P1-1 存储先迁 PG,再谈其他(R4/R5/R8/R9 的前置)

- **问题**:见 §0 的三坑咬合。**先加实例是最坏顺序**。
- **方案**:决策判据 ——
  - 当**写并发**是瓶颈(每轮对话多次落库)→ **迁 PG**,这是唯一解锁项,加实例无效;
  - 当只是读多政策问答 → SQLite WAL 已够,**不必迁**;
  - 迁 PG 后**再**把限流与缓存迁 Redis(共享状态),**最后**才开多实例。
- **权衡**:PG 引入运维面(备份、连接池、迁移),而用户**无专职运维** → 建议**云托管 PG**,不自建。Redis 同理用托管单实例,**不上 Redis Cluster**(此规模是过度设计)。
- **落地成本**:PG 切换 + 方言 + 连接池 ≈ **3-5 人日**(含 P0-3 的方言部分,不重复计)。验证方式:全量测试在 PG 上跑一遍 + 写路径压测对比。

### P1-2 限流迁 Redis(R4/R5)

- **问题**:进程内计数器在多实例下阈值失效;`_buckets` 无界。
- **方案**:Redis + Lua 原子扣减(令牌桶),key 按 `subject` / `tenant` 两维;**`INCR+EXPIRE` 天然解决无界增长**。保留 429 + `Retry-After`(**现有实现已正确,不要改成 5xx**)。
- **权衡**:每次限流多 1 次 RTT;阈值漂移 5%-10% 可接受(**经验值**)。Redis 挂了要决定 fail-open 还是 fail-close —— **资损链路建议 fail-close,纯读问答可 fail-open**,需按接口分档。
- **落地成本**:≈ **1.5-2 人日**。验证方式:双实例并发压测,确认集群总放行量 ≈ 阈值而非 2×。

### P1-3 DLQ 闭环(R6)

- **问题**:dead 行落表即终点,无人消费无告警 —— 命中「无 DLQ 消费者」反模式。
- **方案**:①`/metrics` 暴露 `job_dead_total` 与 `job_dead_age`;②阈值告警(积压 >N 或最老 dead 年龄 >T,**阈值待压测与业务定**);③坐席工作台加「死信重放」入口(需幂等,重放携带原 job id)。
- **权衡**:重放入口是**写操作**,必须走 `require_agent` + 幂等,否则成为新的越权面(第四轮 D 系列刚踩过)。
- **落地成本**:≈ **1-1.5 人日**。验证方式:构造耗尽重试的作业,确认告警触发且重放成功且不重复执行。

### P1-4 readiness 与摘流(R7)

- **问题**:`/health` 静态 200。**注意:静态 liveness 本身是对的** —— reference 明确「liveness 探下游 = 级联故障放大器」。缺的是**独立的 readiness**。
- **方案**:①新增 `/healthz/ready` 探 DB(`SELECT 1`);②`/health` **保持静态**作 liveness;③nginx upstream 加 `max_fails` + `fail_timeout` 做被动摘流(compose 形态下没有 K8s readiness 门,只能靠 nginx)。
- **权衡**:readiness 探 DB 会在 DB 抖动时摘流全部实例 → **必须配最小可用实例数或降级开关**,否则从"部分请求失败"变成"全站不可用"。单机形态下这点尤其要小心:**只有一个实例时,摘流 = 全站下线**,所以单机建议 readiness 只用于**告警**不用于摘流。
- **落地成本**:≈ **0.5-1 人日**。验证方式:停 DB,确认 ready 变红、liveness 仍绿、进程不重启。

### P1-5 单 worker 护栏(R9)

- **问题**:口径只写在 docstring 里,**没有代码阻止误用**。下一个人在多进程下起服务就会踩。
- **方案**:`start()` 时若检测到多 worker 配置且 `max_age_seconds is None` → **拒绝启动并给明确错误**。
- **权衡**:增加一个配置校验点;但比"靠注释约束"可靠得多 —— 这正是本项目「确定性护栏优于约定」的既有方法论。
- **落地成本**:≈ **0.5 人日**。验证方式:构造多 worker 配置,确认启动被拒。

### P2 清单(排期)

| 项 | 方案要点 | 成本 |
|---|---|---|

## 6. 拒给容量数字的四件替代交付物

### ① 不依赖流量的确定性判据
§3 的 R2/R3/R6/R7/R9/R13/R14 与 §0 的**迁移顺序判断**,全部不需要 QPS 即成立。

### ② 公式结构 + 解锁所需输入清单

```
N = ceil(Q_peak × k / Q_single_safe)
    k              安全系数,经验区间 1.3–1.5(待压测校准)
    Q_peak         峰值 QPS                          ← 缺
    Q_single_safe  单机安全 QPS(阶梯压测在 CPU ≤60–70% 水位下的拐点) ← 缺
```
**解锁该数字所需输入**:峰值 QPS、均值 QPS、峰均比、SLO(P99 + 错误率预算)、单机规格、
压测数据量与生产比例、缓存命中率假设。**以上任一缺失,本公式只给符号形式。**

### ③ 指标采集路径

| 要拿的量 | 从哪拿 | 现状 |
|---|---|---|
| P95/P99/P999、错误率、吞吐 | 压测工具(k6/locust)侧统计 | **未建** |
| CPU/内存/连接池/队列深度 | `/metrics`(已实现,三态门控)+ Prometheus(配置已有) | **从未运行验证** |
| 写路径拐点 | 压「对话落库 + 入队 + 消费」全链 | **未建**,且这是 SQLite 的真实瓶颈 |
| SSE 首字节延迟 | 压 `/api/c/chat/stream`,单独统计 TTFB | **未建** |
| 冷启动 P99 / 最长请求 | 容器启动计时 + 压测最长响应 | **未测**(决定 grace 与探针参数) |

### ④ 当下即可执行的 P0 动作(不需要任何流量数字)

## 9. 核验结论(把报告里的「待核验」逐条落实)

### 9.1 R12 熔断:读全后**结论要改**,而且发现两条正面事实

读全 `llm/router.py` 状态机后:

| 项 | 核验结果 |
|---|---|
| 半开探测数 | `half_open_limit=1`,确认样本过小 |
| **冷却递增** | **确认没有** —— `recovery_timeout` 固定 30s;半开探针失败只把 `_opened_at` 重置为当前时刻,**下次仍是 30s**。下游长期不可用时会**每 30s 撞一次满超时,永不退避** |
| 失败判定口径 | **正面**:`is_circuit_failure()` 只把 5xx / 429 / 超时 / 网络错误计入;**401/402/403 等配置类 4xx 明确不计入** —— 正确避开「熔断统计含业务异常」反模式 |
| 流式失败切换 | **正面**:`if emitted or not is_circuit_failure(exc): raise` —— **已吐出部分字节的流不做档位切换**(不能把已发出的字节收回),设计正确 |
| 统计窗口 | `failure_threshold=3` 连续失败,**无滑动窗口、无最小请求数**。低 QPS 下这是合理的简化策略,但**属对 reference 判据的有意偏离,应写进文档**而非当作缺陷 |

→ R12 的实质缺陷收敛为**「冷却不递增」**一条(仍 P2,因为有降级链兜底);其余转为正面结论与文档补充。

### 9.2 R14 PII 出口矩阵:**两处确凿机制缺口 + 三处干净**

按第四轮方法论枚举「用户原文/PII」的全部出口:

| 出口 | 是否带用户原文 | 守卫 | 结论 |
|---|---|---|---|
| 应用日志 | **否** | 全仓 29 处 logger,涉外部调用的 2 处只记**异常类名**与固定文案 | ✅ 干净 |
| `/metrics` | **否** | 标签只有 `node` / `quantile` / `direction`,低基数、无 customer_id | ✅ 干净 |
| 评测报告 JSON/MD | **否** | `eval/report.py` 只写聚合指标,无 reply 正文 | ✅ 干净 |
| **`turn_audit.reply`** | **是,对客回复全文** | **无脱敏、无 TTL**,且该表**设计上比业务数据活得久**(模型注释明写「业务数据被删除后仍可留存」) | ❌ **留存风险** |
| **坏例草稿 → 评测集** | **是,买家原始消息** | **无脱敏**;`promote_badcase.py` 把 `message.content` 直接写成草稿的 `user_input` | ❌ **PII 出仓风险** |
| `badcase.transcript` | 是(DB 内) | agent-only 访问 | ⚠️ 留存期未定 |

**出仓风险已核实到具体路径**:`data/eval/drafts/` **未被 gitignore**(`git check-ignore` 无输出),
且目录里**已有两个被 git 跟踪的草稿文件**。
⚠️ **当前样本恰好干净**:现存草稿 `user_input` 是「我要退款,这个订单一直不发货」,**不含手机号**。
所以这是**机制无守卫**,不是**已发生泄露** —— 但真实买家一句「我的号码138…,订单不发货」
就会经坏例草稿**提交进 git 仓库**,且入集后成为冻结评测资产,清理成本极高。

→ R14 由「P2 待核验」升级为 **P1 确凿机制缺口**(两条),并保留三条正面结论。

### 9.3 R7 nginx 摘流:措辞要更准

`upstream copilot_backend { server backend:8000; keepalive 32; }` —— 无显式 `max_fails/fail_timeout`。
但 nginx **默认就是 `max_fails=1 fail_timeout=10s`**,所以"没配被动健康检查"的说法不准确。
**真正的原因是上游只有一个 server**:无处可切,失败标记没有意义。
→ 单机形态下 readiness **只能用于告警,不能用于摘流**(摘流 = 全站下线),这条原判断成立且更明确。

### 9.4 R11 优雅停机:确认无应用层排空

`lifespan` 退出分支只做三件事:停 SLA 调度器、`jobs.stop_worker(engine)`、`engine.dispose()`。
**没有应用层 in-flight HTTP/SSE/WS 排空**,依赖 uvicorn 自身;
而 compose 无 `stop_grace_period`(默认 10s),WS 侧 `proxy_read_timeout 3600s`。
→ 长连接在停机时会被 SIGKILL 截断,R11 成立(P2)。

### 9.5 **核验中新发现的一条(报告原稿没有)**

**`lifespan` 用 `Base.metadata.create_all(bind=engine)` 兜底建表,绕过 Alembic。**
`create_all` 只建**缺失的表**,**从不 ALTER 已存在的表** ——
这正是本轮 F1 中 `dev.db` 缺 `delivered_at` 却"看起来能起"的机制原因。
生产启动若只靠 `create_all`,**schema 会静默漂移于迁移链**。
→ 新增 **R15(P1)**:启动应校验 `alembic_version` 是否等于 head,不等则拒绝启动或显式告警;
`create_all` 只保留给测试/演示路径。

### 9.6 工具与运行时可用性(**决定哪些能做、哪些做不了**)

| 依赖 | 本机 | 影响 |
|---|---|---|
| `httpx` / `anyio` | **有** | 压测驱动可零新依赖自研 |
| `pytest-cov` / `coverage` | **无** | R2 需装 dev 依赖(**不动生产锁文件**) |
| `locust` / `k6` | **无** | 不装,改用 httpx+asyncio 自研驱动 |

| **`psql` / PG** | **无** | **PG 迁移与方言无法验证** |

## 13. R17(P0,新增):nginx 只反代 `/api/`,部署栈实际登不进去

**发现方式**:新加的 `container` job 真 build 镜像 + `compose up backend nginx`,经 nginx 冒烟。
前三步(静态页 / liveness / readiness)全 200,**第四步 `POST /auth/login` 404**。

| 项 | 内容 |
|---|---|
| **风险** | 应用 51 条 OpenAPI 路径分 8 个顶层段,nginx 只反代 `/api/`;`/auth` `/orders` `/refunds` `/tickets` `/v1` 共 **19 个端点**落进静态 `location /`(`try_files … =404`) |
| **严重度** | **P0** —— 不是"少一个接口":登录、订单全部读写、退款申请/审批/打款/驳回、工单全部读写在部署栈上**全不可用** |
| **影响面** | 任何按本目录部署的实例。**前端 UI 同样坏**:`agent.js:79` 调 `/auth/me` 校验登录态、`:529` 调 `/orders/{id}`、`:542` 调 `/tickets/{id}`,全部 404。开发态用 uvicorn 直连**不受影响**,所以本机与全部测试都看不出问题 |
| **证据** | CI container job 冒烟步骤原始输出(404 + 随后 JSONDecodeError);`deploy/nginx.conf` 原六个 location;`app.openapi()` 路径枚举 |
| **建议动作** | 补五个 location + **两条永久守卫**(已落地) |

**为什么四轮安全审计 + 静态 lint 都没抓到(方法论层)**:
- 静态 lint 查"键齐不齐"(有没有 `proxy_pass`、`/metrics` 有没有 allow/deny),**不查覆盖完整性**;
- 全部 API 测试用 `TestClient` **直连 app**,根本不经过 nginx;
- 这是「同一份请求的不同出口没过同一道守卫」的又一例 —— 这次的出口是**反向代理层**,
  此前四轮枚举的都是应用内出口(REST / WS / SSE / prompt / 缓存 / 日志),**从未枚举过代理层**。
  → **新增固定检查项:凡有反向代理/网关,必须把「应用全部对外路径 × 代理转发规则」做笛卡尔核对。**

**修法(不硬编码前缀清单)**:
1. nginx 补 `/auth` `/orders` `/refunds` `/tickets` `/v1`。
   ⚠️ **不能带尾斜杠**:`GET /orders` `/refunds` `/tickets` 是裸路径;
   而去掉尾斜杠有误吞同名静态文件的风险(前端 `api.js` 正是 `/api/` 必须带斜杠的原因),已核对无撞名。
2. 两条守卫(先红后绿,红时精确列出 19 条):
   - 从 `app.openapi()` 取**全部真实路径**,按 nginx 匹配语义算出命中的 location,断言必须 `proxy_pass`;
   - **反向守卫**:枚举 `frontend/` 全部文件断言仍走静态,防止修复反过来打断前端;
     内含**门禁有效性自检**(合成去掉尾斜杠的 `/api`,确认匹配器真会把 `api.js` 判给它)。
3. 顺带把 `lint_artifacts.py` 的 `check_ci` 从四门禁扩到**六门禁 + 每 job 超时**,
   并校验 `pg-redis` 真起 PG/Redis 且验迁移双向、`container` 真 build 镜像且验停机 ——
   否则这两个 job 被误删,lint 原先**根本不看**,又退回"写了但没验"。
